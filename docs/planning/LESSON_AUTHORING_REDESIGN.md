# Lesson Authoring Redesign

**Status:** Design only. Implementation happens on its own branch (e.g. `feature/lesson-authoring-redesign`), **after** `fix/bugs-and-improvements` is merged. Nothing in this document is implemented yet.

## 1. Problem statement

Today, creating a new lesson means running `daskalo generate`, answering a couple of Click prompts (book, chapter — topic/interests/length are CLI flags), and letting the LangGraph pipeline invent the entire passage from a short topic string. The operator's actual workflow is different: they have a conversation with an external LLM (ChatGPT) to co-write the lesson's ideas/passage first, then have no good way to feed that result into the pipeline — it can only be used as inspiration for the `--topic` string, or hand-packaged into a ZIP via `daskalo upload` (bypassing the pipeline entirely, including review, media generation, and packaging).

Goal: make that authoring conversation happen **inside opencode**, with the same curriculum-aware guidance a well-crafted ChatGPT prompt would need, and end with the existing pipeline doing what it already does well (vocabulary/grammar extraction, exercises, media, review, packaging, ingest) — without touching `content-cli` itself.

## 2. Decisions made (recap)

| Question | Decision |
|---|---|
| What does the outside conversation typically produce? | Passage **ideas** — not a full lesson (vocab/grammar/exercises still generated by the pipeline). |
| Where should this live? | An opencode slash command + skill — not a change to `daskalo`'s CLI, and not ChatGPT-specific (ChatGPT was just what was accessible). |
| Should there be a curriculum-aware "brief" step? | **Yes** — before brainstorming, surface CEFR level, target grammar, mandatory vocabulary, accumulated knowledge, and the pipeline's hard content rules, so the conversation can't drift somewhere the pipeline will fight it. |
| How strict should the pipeline be with provided content? | **Review + report, never rewrite.** The existing reviewer already only evaluates and never edits (`REVIEW_CONTENT_PROMPT`: "Do not rewrite, only evaluate") — nothing changes here, but any review warnings must be surfaced back to the user, not silently swallowed. |
| Is a content-cli code change acceptable (e.g. an additive `--seed` flag) so the passage survives verbatim? | **No.** Zero changes to `content-cli/`. The approved draft steers `draft_lesson_core`'s generation instead of bypassing it — see §7 for the explicit tradeoff this implies. |
| How automatic should the flow be? | **Fully automatic** — after the user approves the draft, the agent writes the CLI invocation, runs it, watches output, and reports results back — no manual copy/paste of commands. |
| Where should output land? | **Local emulator first** (today's default), same as the existing `daskalo generate --local` behavior. Production upload stays a deliberate, separate `daskalo upload --remote` step. |

## 3. Non-goals

- No changes to any file under `content-cli/` (confirmed decision above — this also means `main.py`'s interactive flow, flags, and defaults are untouched).
- No ChatGPT/external-LLM integration of any kind.
- No new Firestore fields or schema changes.
- No production auto-ingest — `--no-local`/`upload --remote` remain manual, deliberate steps.

## 4. Architecture

Two new files, created on the future implementation branch:

```
.opencode/commands/lesson.md          # thin slash-command trigger, /lesson [chapter-id]
.opencode/skills/lesson-author/SKILL.md   # the actual multi-step workflow
```

Per opencode's documented command format (`.opencode/commands/<name>.md`, frontmatter `description`/`agent`/`model`, body = prompt template, `$ARGUMENTS`/`$1` for positional args), `lesson.md` does nothing but pass the optional chapter-id argument through and tell the agent to load the skill:

```markdown
---
description: Author a new Daskalo lesson through conversation, then generate it.
agent: build
---
Load the `lesson-author` skill and run an interactive lesson-authoring session
for curriculum chapter "$ARGUMENTS" (if empty, ask the user which chapter to work on).
```

All actual logic — the brief, the conversation guidance, the generation handoff — lives in the skill body, following this repo's existing convention (thin command, detailed skill).

## 5. Workflow

### Step 1 — Preconditions

- Confirm the local stack is reachable (Firestore emulator on `8081`, Storage emulator on `9199` — same ports `dev.sh`/`local_ingest.py` already assume). If not running, tell the user to start `./dev.sh` first (needed later for local ingest, not for the conversation itself).
- Confirm `content-cli/.env` has `GOOGLE_CLOUD_PROJECT` set (required by `daskalo generate` even in `--local` mode, per `main.py:543-549`).

### Step 2 — Chapter selection & coverage check

- Read `shared/data/books/book_*.yaml` directly (no content-cli code involved) to list books/chapters.
- Best-effort "already generated?" signal: check `content-cli/output/*.zip` for a variant whose name starts with the candidate chapter ID, and — if the emulator is reachable — cross-check `chapters` in the Firestore emulator via its REST API. This is informational only (multiple variants per chapter are supported by the data model), never blocking.
- Resolve `book`, `chapter`, and the chapter's `suggested_length`.

### Step 3 — Generate the brief

Reuse the pipeline's **exact** existing logic instead of reimplementing it, by shelling out to the already-shared `shared/data/curriculum_loader.py` functions (no new file, no content-cli change — this is the same module `content-cli/nodes/build_context.py` imports):

```bash
PYTHONPATH=. uv run --project content-cli python - <<'PY'
from pathlib import Path
from shared.data.curriculum_loader import load_curriculum, find_chapter, get_previous_chapters_vocabulary
# replicate build_context.py's prior-chapter accumulation for the chosen chapter_id
# and print CEFR level, target_grammar, mandatory_vocabulary, accumulated_grammar,
# accumulated_vocabulary as JSON.
PY
```

This guarantees the brief can never drift from what `build_context.py` will actually compute at generation time, because it calls the identical functions.

The brief presented to the user includes:

- **CEFR level** (from the book's `level`), **language skill focus** (`language_skill`)
- **Target grammar** (verbatim `target_grammar` text — these concepts must be featured heavily)
- **Mandatory vocabulary** (must appear in the passage)
- **Accumulated grammar / vocabulary** from prior chapters (may be used freely, per `build_context.py`'s dedup logic)
- **Length options** with their exact sentence-count ranges from `LESSON_CONFIG` (`short` 8-12, `medium` 12-20, `long` 20-30 sentences) so the co-written draft is scoped correctly
- **Hard pipeline rules** the draft must respect, taken verbatim from `DRAFT_LESSON_CORE_PROMPT`:
  - No dialogue or direct speech anywhere in the passage (single continuous narrator voice)
  - Era/tone rule: modern topics → warm conversational tone with light, non-repetitive slang; historical/mythological topics → formal third-person narration, no modern slang
  - Simplify for language acquisition, but never fictionalize real historical events

### Step 4 — Conversation

Brainstorm the scenario/story with the user, iterating a draft passage (Greek attempt + English gloss is optional — Gemini will regenerate the actual Greek regardless, see §7) until the user approves it. The mandatory vocabulary list from the brief should be checked off explicitly during this step.

### Step 5 — Handoff to `daskalo generate`

Once approved, condense the conversation into:
- `--topic`: a rich seed string — scenario summary + key story beats + the approved draft passage, explicitly labeled ("follow this draft closely") — not just a one-line topic like today's manual flow
- `--interests`: student interests surfaced during the conversation (defaults to `"general"` if none came up, matching today's CLI default)
- `--length`: the chosen length

Then run, fully non-interactively (verified: `daskalo generate` only prompts for values missing from the command line — supplying `--curriculum-chapter` and `--topic` skips both prompts in `main.py`):

```bash
uv run daskalo generate \
  --curriculum-chapter <chapter_id> \
  --topic "<condensed seed>" \
  --interests "<interests>" \
  --length <length> \
  --local
```

Watch the run to completion (this already includes `build_context` → draft → extraction → grammar notes/exercises → grammar summary → **review** → media → packaging → local ingest, unchanged).

### Step 6 — Report back

- Reviewer verdict: if `review_content` required a regeneration retry, or if it proceeded past `MAX_RETRIES` with unresolved feedback (`review_content.py`'s existing warning path), surface that to the user as a warning — **never** silently rewrite the approved draft or auto-accept.
- Media warnings: any TTS/image generation failures logged during `generate_media` (currently silent-skip in the pipeline — this redesign doesn't change that behavior, just makes the operator aware of it in the report).
- Ingest result and the local ZIP path (`content-cli/output/{variant_id}.zip`).
- Next actions to offer: verify the chapter at `http://localhost:4200`; optionally chain `uv run daskalo generate-practice output/<variant>.zip`; print (not run) the exact `uv run daskalo upload output/<variant>.zip --remote` command for when the user is ready to publish.

## 6. Fidelity tradeoff (explicit, accepted)

Because `content-cli` is not being modified, the approved draft passage **steers** `draft_lesson_core`'s Gemini call rather than surviving verbatim — that node always generates its own `passage` field and there is no way to inject a pre-written one without a code change. In practice, a strongly-worded seed ("follow this draft closely, reuse these exact sentences where possible") gets close but not guaranteed-identical output.

**Deferred fallback (not being built now):** if verbatim fidelity turns out to matter in practice, a minimal additive `--seed <file>` flag on `daskalo generate` could pre-populate `passage`/`chapter_title` in the initial state and route the graph's entry edge to skip `draft_lesson_core` straight into the `extract_vocabulary`/`extract_grammar_outlines` fan-out (both nodes already operate purely on `state["passage"]`, so no other node would need to change). This was explicitly rejected for the initial version and should only be revisited if the steering approach proves insufficient.

## 7. Acceptance test (for the implementation branch)

1. Run `/lesson b1_c1` (or any un-generated chapter) end-to-end against the local emulator stack (`./dev.sh` running).
2. Confirm the brief presented matches what `build_context.py` would compute for that chapter (spot-check against `shared/data/books/book_1.yaml`).
3. Confirm the generated chapter appears correctly at `localhost:4200` and its Firestore document shape matches `docs/DATA_MODEL.md`.
4. Confirm a rejected-then-approved reviewer cycle (force a low-quality seed) surfaces a warning rather than failing silently.
